# RESTORE-01.3 — защита от устаревших клиентов (проект)

Статус: **спроектировано, НЕ развёрнуто**. Не применять к production до тестового стенда и согласованного переключения клиентов.

## Подтверждённые факты
- Таблица public.move_spaces: id uuid, owner_id uuid, payload text, updated_at timestamptz.
- Старый клиент напрямую выполняет GET и POST upsert в move_spaces.
- Новый RESTORE-01.2 использует restoreEpoch **внутри шифрованного payload**; сервер не может проверить это поле.
- Поэтому **client-only restoreEpoch не защищает от старого клиента**: тот может перезаписать облако старым payload.

## Требуемый контракт
1. Сервер хранит незашифрованный монотонный revision (только метаданные), payload остаётся AES-GCM.
2. Клиент читает payload + revision, рассчитывает merge только при совместимой эпохе.
3. Запись — атомарный compare-and-swap: update только при совпадении expected_revision, увеличивая revision на 1. Конфликт → повторно прочитать и разрешить.
4. Restore — атомарная запись нового payload и increment revision; клиентам передаётся restoreEpoch внутри ciphertext. На конфликте restore отменяется и требует повторного подтверждения/резервной копии.
5. **Прямые INSERT/UPDATE/DELETE для роли authenticated отозваны**. Запись только через строго авторизованный RPC с проверкой auth.uid() = owner_id, без возможности указать чужой id.
6. Старый клиент может читать, но его прямой POST получает 403 и **не может вернуть удалённые предметы**.
7. Вновь подключённый новый клиент при несовпадении restoreEpoch принимает облачный снимок, не отправляя локальные старые записи.
8. При восстановлении сначала скачать резервную копию, затем зафиксировать серверную замену; локальное состояние менять только после подтверждения сервера.

## Критический порядок выпуска
- Сначала подготовить миграцию и RPC на отдельном тестовом Supabase-проекте/ветке (не production).
- Подключить Preview к тестовому backend и провести QA: два новых клиента, старый клиент, офлайн-клиент, конкурентные записи, неправильная учётная запись, неудачный запрос.
- Подготовить новый клиент с RPC. **Нельзя** просто отозвать запись в production до готовности нового клиента: это временно остановит сохранение для всех текущих пользователей.
- На production провести контролируемое переключение: миграция RPC + ограничение прямых записей + новый клиент; проверить и иметь план отката.
- Не проводить тесты с пользовательским production payload.

## Тестовые критерии
- Старый клиент после restore: POST upsert отклонён, данные не меняются.
- Новый клиент с revision N: CAS(N) успешен → N+1; повторный CAS(N) отклонён.
- Офлайн-клиент после restore: скачивает новую эпоху, заменяет локальное состояние.
- Два конкурентных restore: только один CAS успешен.
- Ошибка сети / шифрования: локальные данные не заменяются.
- Владелец A не может прочесть/изменить строку B.

## Нерешённое
- Нужен тестовый Supabase backend для проверки миграции без риска production.
- Выбрать UX для устаревшего клиента: предложение обновить страницу после 403.
- Реализовать и проверить RPC + CAS в приложении; текущий RESTORE-01.2 **не выпускать**.
